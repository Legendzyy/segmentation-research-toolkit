# 从具体问题到可辩护论文：通用设计工作流

本文是一套研究设计方法，不是一份已经冻结的实验计划。适用于围绕明确视觉任务提出方法、适配成熟组件或组织工程研究；不要求每个问题都必须覆盖所有数据集，也不把有限任务上的经验结果扩展为普遍规律。

学习顺序：先写出第一节的一句话问题，再选第三节实际需要的比较，用第四节列出一个替代解释，最后填写 claim—evidence 表。不要把本文所有实验类型都列成必做任务。想练习判断时读 [失败案例](FAILURE_CASES.md)；想看文件怎样衔接时读 [完整教学示例](../examples/synthetic_study/README.md)。

## 1. 先写清楚问题，而不是先列模块

用一句话说明：**在什么任务、哪些现实约束下，现有系统出现什么可重复的失败，我们希望改善哪个结果，并承担什么代价。**

需要的起点是该系统自己的证据。来自其他模型、其他数据或早期不同配方的错误分布，只能提供动机，不能直接代替当前系统的诊断。

| 要素 | 应回答的问题 |
|---|---|
| 任务 | 谁需要什么输出？哪些样本或条件特别困难？ |
| 失败 | 是漏检、排序、定位、形状、数值稳定性还是资源问题？ |
| 约束 | 哪些模块必须固定？可改变哪些训练与推理部分？ |
| 主指标 | 什么变化才算解决问题，而不是改善代理量？ |
| 代价 | 训练成本、推理成本、标注要求与适用范围是什么？ |

可以先提出直觉，再用证据检验；无需先拥有完整因果解释才允许探索。但论文不能把探索后的解释写成事前已知事实。

## 2. 让设计与问题一一对应

为每个主要设计写出三个句子：它改变了什么计算；为什么可能缓解已观察到的失败；如果假设错误，会出现什么可测量的反例。

准确描述改动位置。新增训练约束、增加附加模块、修改输出规则、替换整个架构是不同的贡献与成本范围。实现中存在一个组件，不等于它应被列为独立创新点。

成熟组件可以构成有价值的新研究。新意可能在任务定义、组合中的交互、领域约束、具体适配、机制解释或评价范式，而不是每一个算子都从未出现。需要引用来源并说明真正的设计差异，避免将已有运算重新命名为原创。

## 3. 把四类比较分开

| 比较层级 | 回答的问题 | 解释限制 |
|---|---|---|
| 同底座方法比较 | 这项修改本身带来什么变化？ | 尽可能固定权重、数据、候选与评价 |
| 简单强对照 | 更简单的训练、容量或输入调整能否解释收益？ | 不能因为它更强就删除 |
| 成熟机制近邻 | 同类既有思想是否已经达到相近效果？ | 适配必须明确，不冒称官方全复现 |
| 完整系统比较 | 新系统在任务中的实际位置是什么？ | 总差值包含底座、预训练与配方差异 |

文献 reported results 与本地统一评价分表或明确分列。不能把不同划分、分辨率、标签处理与 checkpoint 规则的数据混在一个排名里。

公平不必等同所有模型使用完全相同的优化器；合理原生配方可以保留，但要诚实说明它是系统级比较。相同 epoch 也不代表相同训练预算。

## 4. 用最小消融区分竞争解释

不要只问“A+B 比 baseline 高不高”。先写出竞争解释，再选择能区分它们的对照。

| 观察 | 可能的替代解释 | 有信息量的对照 |
|---|---|---|
| 新损失改善结果 | 只是训练更久或监督量更大 | 同总预算、同有效监督量的简单控制 |
| 更细表示改善结果 | 只是插值、算力或容量增加 | 固定插值控制、算力匹配、来源×分辨率阶乘 |
| 更复杂目标有收益 | 只是修正整体校准或权重尺度 | 在允许训练角色内拟合的简单校准控制 |
| 某子群指标改善 | 匹配集合或漏检发生变化 | 全部 GT coverage、共同身份配对及未匹配分析 |
| 模块组合有收益 | 一个主模块已解释全部提升 | 单组件、组合、简单强参照及交互对比 |

如果一次比较同时改变目标来源和损失权重，就不能单独归因给来源。资源不足时可以收窄 claim，不必为追求完整表格仓促启动无法解释的实验。

模块级贡献需要模块级证据。不同版本或不同参数化上的旧消融不能直接代填最终方法的逐组件效应。反过来，没有被主张为独立贡献的实现细节，也不必强求每一项都有一行下降结果。

## 5. 让敏感性分析回答具体问题

优先级应由证据缺口决定，而不是枚举全部超参数。

- 资源预算是否真正触发瓶颈？先看实际使用分布，再决定是否画预算曲线。
- 方法依赖的先验在什么条件下可靠？预定义分层、保留所有组和样本数，GT 只用于解释，不能进入部署选择。
- 结果是否依赖训练随机性？明确重复的是附加模块、完整系统还是数据划分，不将它们混称多 seed 验证。
- 改推理输入范围是否改变训练分布？这种敏感性不能直接当作最优训练设计比较。

预定默认配方保持固定，敏感性曲线用于说明范围。若根据曲线重新选择参数，应明确回到开发阶段，重新安排未参与选择的确认。

## 6. 将端点、机制与成本连成证据链

主结果优先回答任务目标，机制分析解释变化发生在哪里，失败案例界定何时不成立。不能用某个容易改善的代理量代替任务目标，也不能因为完整指标上涨就认为所有模块都被证实。

数学关系可以说明条件下的性质，但不能证明输入假设总是正确或实际系统必然受益。将“给定条件下可推出的结论”与“这些条件在真实数据上是否满足”分别验证。

新增参数很少只支持附加模块紧凑。整体参数更少、训练更省、推理更快和精度成本更优是四个不同结论，需要相应实测。若方法只提供质量成本交换，直接以该交换定位论文。

## 7. 冻结确认之前把比较对象选完整

建议顺序：

1. 确定任务范围、主 claim 和关键替代解释。
2. 冻结有限开发计划，包括简单强对照、核心消融与必要成本测量。
3. 完成开发，保留所有候选、负结果和修订原因。
4. 在未见确认或最终内容前，固定模型、端点、对照、统计与 checkpoint 规则。
5. 完成工程检查，再依照具体授权访问确认或最终数据。
6. 按预定顺序分析，报告偏离协议及其原因。

观察了某域的结果后再收窄主张范围，可以成为合理的研究更新，但必须保留时间线，不能写成始终如此的事前设计。既有确认结果被用于修订后，即成为已见开发证据。

## 8. 根据证据定位贡献

| 证据 | 可以主张 | 还不能主张 |
|---|---|---|
| 某任务的独立同协议改善 | 对该任务有价值的方法或适配 | 对任意任务普遍有效 |
| 多个同 seed 配对方向一致 | 在所测随机性范围内重复 | 不受所有训练变化影响 |
| 一项 oracle 显示余量 | 该诊断约束下存在改善空间 | 已有可部署方法能实现该空间 |
| 部分局部质量提高，完整主指标不稳 | 混合结果及具体局部现象 | 已可靠解决最终任务 |
| 简单控制匹配复杂设计 | 更简约解释值得优先 | 所有类似复杂方法均无效 |

单一数据集可以定义有价值的任务；独立评价和公平强对照仍然提高可信度。跨域与跨底座迁移属于进一步主张，需要相应证据，不必把它们强行设为所有论文的必要条件。

## 9. 把论文写成问题的回答

正文结构可以是：

1. **引言**：任务需求、当前失败、具体问题及拟解决范围。
2. **相关工作**：按机制与问题组织，交代已有思想和本工作的差异。
3. **方法**：明确固定和改变的部分、算法、训练与部署信息、复杂度。
4. **实验设置**：数据角色、比较层级、训练预算、评价与统计契约。
5. **结果**：主比较、系统位置、核心消融、机制与失败、稳定性和成本。
6. **讨论**：强对照优势、剩余限制、范围外现象与尚不能识别的解释。
7. **结论**：回答开头的问题，不把实验数量或审计数量当贡献。

主文可以优先保留系统比较、核心消融、稳定性/coverage 和实际成本四类表；方法图、动机与失败案例、质量成本关系补足解释。详细实验分支、协议偏离和 replay 记录进入可定位的补充材料。

使用 [claim—evidence 模板](../templates/CLAIM_EVIDENCE.md) 逐条检查：每个贡献有哪份证据，哪些反证仍在，哪些表述必须降级。审计提供可信度，具体问题与研究发现才是论文中心。
